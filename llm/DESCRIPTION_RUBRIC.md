# 파티·샘플 설명문 평가 기준 (하네스용, rubric v1 · 2026-10-23)

`DESIGN.md` 5단계: 하네스가 파티·샘플마다 설명을 미리 써서 DB에 저장한다.
설명이 한 번에 통과하기는 어려우니 **쓰기 → 검사 → 고쳐 쓰기**를 반복하고, 이 문서를 통과한 것만 저장한다.

```
근거 묶음 만들기 → 작성 → [1차] 자동 검사(코드) ─실패→ 고쳐 쓰기 (실패 항목만)
                              │ 통과
                              ▼
                        [2차] 심사(AI 채점) ─미달→ 고쳐 쓰기 (지적 항목만)
                              │ 통과
                              ▼
                        저장 (status=passed)   ※ 3번 고쳐도 안 되면 status=needs_review (사람 검수)
```

## 0. 근거 묶음 (작성·심사 모두 이것만 본다)

설명에 쓸 수 있는 사실은 하네스가 DB·back 도구로 미리 뽑아 준 **근거 묶음** 안의 것뿐이다. 작성 모델이 외운 지식으로 숫자·사용률·상성을 채우지 않는다.

| 대상 | 근거 묶음 내용 |
|---|---|
| 샘플 | 포맷, 포켓몬(메가면 메가 폼)·타입·종족값, 특성·도구·성격·SP(0 생략)·기술 4개, 기술·특성·도구 한글 설명(나무위키), `member_profile` 역할, 그 포켓몬 샘플의 형태 분포(shapes), 같은 포켓몬 다른 샘플과의 차이(도구·SP·기술), 출처(OP.GG/대회 이름·순위) |
| 파티 | 포맷, 6마리 각 샘플 요약 + 역할, `check_party`(역할·밸런스·중복·메가 수·경고), 겹치는 약점, `find_threats` 상위, 출처(OP.GG 상위/대회 이름·순위·선수) |

- 근거 묶음에 없는 것은 쓰지 않는다. 묶음에서 **계산한 값**(예: 메가 후 스피드 종족값 +30)은 `derived`로 같이 넘겨 숫자 검사에서 허용한다
- 심사 모델에게도 같은 묶음을 준다 (묶음 밖 지식으로 "틀렸다"고 하지 않게)

## 1차: 자동 검사 (코드, 하나라도 실패하면 바로 고쳐 쓰기)

학습 데이터 검사(`training/make_data.py`의 `numbers_grounded`·`names_grounded`·`FOREIGN`)를 그대로 재사용한다.

| # | 항목 | 실패 조건 |
|---|---|---|
| A1 | 숫자 근거 | 설명 속 숫자가 근거 묶음·`derived`에 없음 (승률·데미지%·확정타·"상위 5%" 같은 지어낸 수치 포함) |
| A2 | 포켓몬 이름 근거 | 묶음에 없는 포켓몬 이름 (위협·파트너도 묶음에 있는 것만) |
| A3 | 기술·특성·도구 근거 | 샘플에 없는 기술·특성·도구를 "가지고 있다"고 씀. 파티 설명이면 6마리 샘플 안에 있어야 함 |
| A4 | 역할 모순 | `member_profile` 역할과 반대되는 말 (CS 딜러를 "막이", HBD+깨불을 "딜러"라고 함) |
| A5 | 포맷 용어 | 더블 설명에 "기점잡이", 싱글 설명에 더블 전용 운용(속이기 견제·날따름 보호 등)을 주된 역할로 씀 |
| A6 | 출처 표기 | 출처·대회 이름·순위가 DB(`Team.source`·`event`·`placement`)와 다름. 리플레이를 근거로 씀 |
| A7 | 글자 | 외국 글자(`FOREIGN`), 마크다운(`**`, `#`, 표, 글머리표), 이모지, back 도구 이름(`check_party` 등) |
| A8 | 길이 | 샘플 60~220자, 파티 120~400자 (공백 포함). 문장 2~4개 / 3~6개 |
| A9 | 단정·과장 | "최강", "무조건", "필수", "완벽", "절대", "카운터 없음", "승률이 높다" |
| A10 | 중복 | 같은 포켓몬의 다른 샘플 설명(또는 다른 파티 설명)과 문장 유사도 0.8 이상 — 이름만 바꾼 템플릿 문장 금지 |
| A11 | 메가 | 메가 폼을 메가 전 이름으로 부름, 메가스톤 3개 이상 파티인데 선출 제한 언급 없음, 메가 2마리 이상 동시 선출을 권함 |

## 2차: 심사 (AI 채점)

자동 검사로는 못 잡는 "게임적으로 맞는가, 쓸모 있는가"를 본다. **작성 모델과 따로 부른 심사 모델**이 근거 묶음 + 설명을 보고 항목마다 0/1/2점을 준다.

### 공통 항목

| # | 항목 | 2점 | 1점 | 0점 | 필수 |
|---|---|---|---|---|---|
| J1 | 게임 정확성 | 기술·특성·도구 효과를 바르게 씀 | 표현이 애매하지만 틀리지는 않음 | 효과를 잘못 앎 (예: 구애스카프가 방어를 올린다) | **2점 필수** |
| J2 | 역할·운용 일치 | 역할을 SP 분배와 기술 배치로 설명 | 역할은 맞지만 근거가 종족값뿐 | 역할이 틀림 | **2점 필수** |
| J3 | "왜"가 있음 | 도구·SP·기술 선택 이유를 연결해서 설명 | 일부만 이유가 있음 | 구성 나열만 ("기술은 A, B, C, D") | |
| J4 | 한계·약점 | 근거 묶음에 있는 약점·막히는 상대·주의점을 짧게 | 막연함 ("상성 주의") | 없음, 또는 묶음에 없는 약점을 지어냄 | |
| J5 | 쓸모 | 읽고 바로 운용에 쓸 정보 (언제 꺼내고 무엇을 먼저) | 일반론 | 정보 없음 | |
| J6 | 문체 | 짧은 "~요" 체, 서버 답 문장(`agent/answers.py`)과 같은 말투, 겹말 없음 | 조금 길거나 딱딱함 | 장황, 번역투, 반말·명령조 | |

### 샘플 전용

| # | 항목 | 2점 | 1점 | 0점 |
|---|---|---|---|---|
| S1 | 차별점 | 같은 포켓몬 다른 샘플과 무엇이 다른지 (도구·SP·기술) 한 마디 | 암시만 | 다른 샘플에도 그대로 맞는 설명 |
| S2 | 흔한 형태인지 | shapes 기준 흔한 형태면 그렇게, 드문 형태(10% 미만)면 "드문 형태"라고 밝힘 | — | 드문 형태를 표준인 것처럼 씀 |

### 파티 전용

| # | 항목 | 2점 | 1점 | 0점 |
|---|---|---|---|---|
| P1 | 컨셉 | 컨셉(균형·스윕·사이클·트릭룸·순풍·단일 타입 등)과 축(메가·에이스)을 첫 문장에 | 컨셉은 있지만 축이 없음 | 컨셉 없음 |
| P2 | 멤버 연결 | 서로 받아 주는 관계, 판 깔기 → 딜러 같은 연결을 2개 이상 | 1개 | 멤버 나열만 |
| P3 | 위협·선출 | `find_threats`·겹치는 약점 중 핵심 1~2개와 대응(누구를 내는지) | 위협만 | 없음 |

### 통과 기준

- 1차 자동 검사 전부 통과
- J1·J2가 2점
- 0점 항목이 없음
- 합계: 샘플(J1~J6 + S1~S2, 16점 만점) **12점 이상**, 파티(J1~J6 + P1~P3, 18점 만점) **14점 이상**

### 심사 출력 형식 (JSON 한 개)

```json
{
  "scores": {"J1": 2, "J2": 2, "J3": 1, "J4": 2, "J5": 1, "J6": 2, "S1": 0, "S2": 2},
  "issues": [
    {"item": "S1", "quote": "빠른 스피드로 상대를 압박하는 딜러예요", "fix": "다른 샘플(생명의구슬)과 달리 구애스카프로 선공을 잡는다는 점을 넣기"},
    {"item": "J3", "quote": "기술은 지진, 역린, 스톤에지, 아이언헤드예요", "fix": "스톤에지가 어떤 상대를 위한 기술인지 근거 묶음의 기술 설명으로"}
  ],
  "pass": false
}
```

- `quote`는 설명에서 그대로 옮긴 문구, `fix`는 고칠 방향 한 줄. 심사 모델은 설명을 직접 다시 쓰지 않는다
- `pass`는 하네스가 점수로 다시 계산한다 (심사 모델의 `pass`를 믿지 않음)

## 고쳐 쓰기 규칙

- 작성 모델에게 **이전 설명 + 실패 항목(1차 항목 번호·걸린 숫자/이름, 2차 `issues`)만** 준다. 지적 안 받은 문장은 그대로 둔다 (고칠 때마다 새 오류가 생기는 것을 막음)
- 최대 3번. 3번째도 실패하면 마지막 설명과 실패 기록을 남기고 `status=needs_review`
- 같은 항목이 2번 연속 실패하면 3번째에는 그 문장을 빼는 쪽으로 지시한다 (못 맞히는 내용을 억지로 쓰지 않음)
- 근거 묶음이 부족해 J4·P3를 채울 수 없으면 0점 대신 `"N/A"`로 하고 만점에서 뺀다 (지어내게 만들지 않음). N/A는 사유를 같이 저장

## 저장할 것

설명과 같이: `rubric_version`(v1), 작성·심사 모델 이름, 날짜, DB 데이터 버전(근거 묶음 해시), 점수, 고쳐 쓴 횟수, `status`(passed / needs_review).
DB를 다시 적재해도 근거 묶음 해시가 같으면 설명을 유지하고, 달라졌으면 다시 검사한다.

## 기준 자체 점검

- 처음 돌릴 때 샘플 20개·파티 10개를 사람이 같은 표로 채점해 심사 모델 점수와 비교한다. 필수 항목(J1·J2) 판정이 3개 이상 다르면 기준 문구를 고치고 `rubric_version`을 올린다
- 통과한 설명 중 5%를 무작위로 사람이 다시 본다. 통과했는데 틀린 설명이 나오면 그 유형을 1차 자동 검사(코드)로 옮길 수 있는지 먼저 본다

## 예시 (샘플)

통과 예 (근거 묶음에 구애스카프·S32·기술 4개·다른 샘플은 생명의구슬형이 있다고 가정):
> 구애스카프로 선공을 잡는 물리 딜러예요. 생명의구슬형과 달리 스피드에 SP를 몰아 상대 스카프·순풍 없는 빠른 포켓몬보다 먼저 지진·역린을 꽂아요. 기술이 묶이니 막이가 나오면 바로 교체하는 게 좋아요.

탈락 예:
> 한카리아스는 최강의 딜러로 승률이 높아요. 지진은 약 60% 데미지를 줘요. 기술은 지진, 역린, 스톤에지, 아이언헤드예요.

- A9 "최강", A1 "60%"(근거 없음), J3 나열만, S1 차별점 없음, J4 한계 없음
